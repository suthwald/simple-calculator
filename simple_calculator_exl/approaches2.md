To achieve **100% recall** (capturing every single high-quality rule) while maintaining **0% duplication** using exactly two LLM calls, you have to shift the responsibility of deduplication to where the LLM is strongest: **semantic clustering**.

Here are the two best engineered architectures to achieve this using precisely two LLM interactions.

---

### Approach 1: The "Exhaustive Dump & Consolidate" Pipeline (Highly Recommended)

Instead of trying to prevent duplicates during extraction, this approach embraces them in the first call to guarantee nothing is missed, and then uses the second call to surgically collapse duplicates based on their true underlying meaning.

```
[Raw Unstructured Text (150k Chars)]
                 │
                 ▼
 ┌──────────────────────────────────────────────┐
 │ CALL 1: The Exhaustive Extractor             │
 │ - Instructed to extract everything raw.      │
 │ - Allows duplicates to maximize recall.      │
 └──────────────────────────────────────────────┘
                 │
                 ▼
      [List of ~600 Raw Rules]
                 │
                 ▼
 ┌──────────────────────────────────────────────┐
 │ CALL 2: The Semantic Synthesizer             │
 │ - Groups similar rules into unique concepts.  │
 │ - Outputs pristine, unique SQLite JSON.      │
 └──────────────────────────────────────────────┘
                 │
                 ▼
     [Pristine SQLite Database]

```

#### Call 1: The Exhaustive Extractor

* **Objective:** Maximize recall. You tell the model to scrape the text line-by-line and dump every single possible rule, even if it feels repetitive.
* **The Prompt:** > "Analyze this unstructured SDLC document. Extract every single engineering rule, best practice, mandate, or standard. Do not worry about duplication or repeating yourself—it is critical that no rule is missed. Output this as a flat JSON array of strings."

#### Call 2: The Semantic Synthesizer

* **Objective:** Eliminate duplication through semantic grouping. You feed the massive array of raw strings generated by Call 1 straight back to Gemini.
* **The Prompt:**
> "You are a master data cleaning engine. Review this raw list of extracted engineering rules. Many are near-duplicates phrased differently across various sections of our documentation.
> Group identical concepts together. For each unique concept, synthesize one clear, authoritative rule statement. Output the finalized list matching this strict schema: [Your Pydantic Schema Here]."



---


To understand how the architecture operate, it is best to look at how they process a piece of messy, repetitive text.

Let's use this snippet of a chaotic Confluence page as our running example:

> **Section 3.1 - Code Submissions:** All PRs need 2 approvals before merging to main. Engineers must use descriptive branch names.
> *(Many pages later...)*
> **Section 7.4 - Quality Gates:** Pull requests cannot be merged without at least two peer reviews. Never commit directly to main.

---

### Approach 1: The "Exhaustive Dump & Consolidate" Pipeline

This approach optimization is focused entirely on **Recall** (ensuring absolutely zero rules are missed). It tells the first LLM call to be greedy and grab everything, leaving the deduplication work for Call 2.

#### Call 1: The Greedy Scraper

You pass the entire document and ask the LLM to pull out every statement that looks like a rule, completely ignoring whether it repeats itself.

* **Output from Call 1:** A raw, repetitive list of strings.
```json
[
  "All PRs need 2 approvals before merging to main.",
  "Engineers must use descriptive branch names.",
  "Pull requests cannot be merged without at least two peer reviews.",
  "Never commit directly to main."
]

```



#### Call 2: The Semantic Synthesizer

You feed that raw list back into the LLM. Because the list is just a few dozen strings (very small), the LLM can easily look at the entire list at once and compress it without hitting output token limits.

* **Output from Call 2:** A pristine, deduplicated Pydantic/JSON dataset.
```json
[
  {
    "rule_statement": "All pull requests require a minimum of two peer approvals before they can be merged into the main branch.",
    "sdlc_phase": "Code Review",
    "original_context": "Section 3.1 & Section 7.4"
  },
  {
    "rule_statement": "Engineers must utilize descriptive naming conventions for all development branches.",
    "sdlc_phase": "Source Control",
    "original_context": "Section 3.1"
  }
]

```
